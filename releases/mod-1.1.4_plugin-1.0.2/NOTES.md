## 改了什么

**修复：服务端导航指令支持指定 Y 轴——楼内/洞穴里的点位不会再被算到屋顶上。**

### 问题

`/startrail nav` 原来只收 `<x> <z>`，Y 由客户端按该列的 `MOTION_BLOCKING` **最高方块**推断。
建筑物内部的点位会被算成屋顶高度，粒子和标点落在楼顶，导航终点在垂直方向就是错的。

### 新用法（两种都支持）

```
/startrail nav <玩家> <x> <y> <z> [导航点名称]     ← 推荐，楼内/地下/洞穴必用
/startrail nav <玩家> <x> <z> [导航点名称]         ← 旧写法保留，Y 仍按地表推断
/startrail nav stop <玩家>
```

判定方式：第 4、5 个参数**都能解析成数字**时按 `<x> <y> <z>` 处理，否则按旧的两维写法。
所以**旧指令与已有脚本不用改**。

### 协议

包 10 在 `string label` 之后追加：

```
boolean hasY    ← 是否指定了 Y
double  y       ← 目标 Y（hasY=false 时发 0）
```

* 新字段全在包尾，老客户端读完 label 就结束，**不会解析错乱**；
* 客户端按「能读就读」处理，老服务端不发也不会崩；
* 未指定 Y 时行为与旧版完全一致。

### 内部变化

`NavigationManager` 新增 `startNav(x, y, z, label)`（`y` 传 `NaN` 表示不指定），
并新增 `targetYExplicit` 标志——**外部指定的 Y 不再被每 5 tick 的路径重算覆盖**。
旧逻辑每次重算都会重新推断地表高度，这正是楼内点位跑偏的直接原因。

## 要不要换 jar

**两端都要换**：

* 客户端 `startrail-forge-1.1.4.jar` → `versions\时之旅者\mods\`（需重启游戏）
* 服务端 `StarTrail-Plugin-1.0.2.jar` → `时旅服务端\plugins\`（**需先关服**）

换完记得同步数据目录的 `language.yml`（见 `docs/DEPLOY.md` 3.0 节）——否则用法提示仍是旧文案。

## 验证情况

* ✅ 两端分别编译通过，`build-mod.ps1` / `build-plugin.ps1` 均成功。
* ✅ **起独立 Paper 测试服（端口 25581）实测**，用线上真实数据目录副本：
  * `v1.0.2` 正常加载，真实数据读出（2 图片 / 2 区域 / 1 传送点 / 318 点位）；
  * 用法提示已更新为 `<x> <y> <z>（省略 y 则按地表推断）`；
  * `nav Nobody 100 64 200 PointXYZ`（三维 + 名称）→ 回复「玩家不在线」，无异常；
  * `nav Nobody 100 200 OldStyleName`（旧两维 + 名称）→ 同上；
  * `nav Nobody 100 64 200`（三维无名称）→ 同上；
  * `nav stop Nobody` → 同上；**全程零异常**。
* ✅ `tools\verify-dist.ps1 -Check` 全绿。
* ⚠️ **未做两端联机的完整实测**：即「服务端下发带 Y 的包 → 客户端收到 → 粒子和标点落在正确的 Y」
  这条链路需要真实玩家进服才能验证。**Y 是否真的生效（而不是被推断覆盖）还没在游戏内确认**。

## 实机确认清单

1. 两端换到 1.1.4 / 1.0.2 并重启。
2. 站在一栋楼的**楼顶**，让 OP 执行 `/startrail nav <你> <楼内坐标X> <楼内Y> <楼内坐标Z> 楼内点位`
   → 粒子和标点应指向楼内那一层，**而不是楼顶**。
3. 同一条指令去掉 Y（`nav <你> X Z 楼内点位`）→ 应回到楼顶（旧行为），以此对比确认 Y 生效。
4. 走完导航 → 距离应变小并在 3 格内自动结束。
